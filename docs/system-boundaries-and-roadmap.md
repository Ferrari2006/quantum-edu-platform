# 系统边界与后续路线

本文回应团队对游戏接入方式、量子计算测试、图形化编程和后续教学重点的讨论。

## 1. 游戏如何接入智能问答

当前采用标准的“状态输入—建议输出”模式：

1. 游戏继续负责规则、回合和量子状态计算；
2. 平台通过`GET /api/quantum-game/state`读取当前状态；
3. AI伴学页面把必要字段放入`game_state`；
4. 调用`POST /api/rag/ask`，并指定`mode=game_strategy`；
5. 多智能体系统返回推荐操作、理由、风险、关联知识和引用；
6. 前端展示建议，用户自行决定是否执行。

这样可以避免AI直接修改游戏内部状态，也方便未来接入其他游戏或外部客户端。

## 2. 两个游戏是否已经变成独立游戏

需要区分“代码模块独立”和“产品完全独立”：

- **代码层面**：两个游戏保留各自的引擎、规则和源码目录，可以分别开发和测试；
- **平台层面**：两者都接入统一的游戏大厅、后端接口和AI伴学，不是与平台无关的孤立产品；
- **运行方式**：原桌面原型可继续单独运行，平台Web版通过适配层复用核心逻辑。

因此，更准确的描述是：**两个游戏模块相对独立，但统一集成在量智启学平台内。**

## 3. “量子计算测试”具体指什么

项目中容易混淆三类能力：

### 开发自动化测试

用于验证代码是否按预期工作，例如RAG检索、引用检查、会话历史、游戏状态机和量子后端计算。这些测试面向开发者，不是学习者使用的功能页面。

### Qiskit代码诊断

AI伴学中的代码纠错会对用户粘贴的代码进行安全静态检查。目前不运行代码，主要发现语法、导入和明显索引问题。

### 面向用户的量子实验

这是未来的教学功能：学习者通过图形化方式拖放H、X、CNOT等量子门，运行线路，并观察状态、概率、Bloch球或保真度变化。

当前仓库已经实现`POST /api/quantum/run`和`POST /api/quantum/fidelity`。前者运行受限的结构化量子线路并返回概率、振幅、Bloch向量和线路指标，后者计算目标态或目标概率分布的保真度。游戏内部量子计算逻辑仍与通用实验服务分开维护。

## 4. 是否需要图形化编程界面

第一版图形化量子线路实验室已经位于`/#/lab`。它与多智能体问答保持模块分离，但支持把当前线路代码一键交给AI伴学解释。

当前MVP已经包括：

- 量子比特线路画布；
- H、X、Y、Z、S、T、RX、RY、RZ、CNOT、CZ和SWAP等量子门；
- 点击放置、删除、撤销和线路清空；
- 结构化线路生成Qiskit代码；
- 运行结果概率图；
- AI解释当前线路及潜在问题；
- 一键把线路问题发送到AI伴学。

下一步可增加自由拖放、三维Bloch球、测量与经典寄存器、噪声模型、实验任务保存，以及Qiskit代码安全解析回线路结构。

## 5. 后续重心如何转向教学

多智能体达到稳定MVP后，当前开发已经开始转向“用户资料库与教学闭环”。第一版已完成：

- 登录用户的统一学习事件记录；
- 文章完成和线路实验自动回传学习证据；
- 21个知识库主题对应的概念目录；
- 概念掌握度加权汇总；
- 知识库首页的个人学习画像和下一步推荐。

下一步继续完成：

1. 完善六阶段知识目录的真实教学内容；
2. 补充文章前置知识、练习和来源审校标签；
3. 接入小测与两个独立游戏的结算事件；
4. 根据薄弱点推荐文章、问题、实验和游戏关卡；
5. 通过小测和任务结果校准掌握度；
6. 建立学习历史与教师分析页面。

最终目标不是让系统生成更多回答，而是让学习者形成“学习—练习—反馈—再学习”的闭环。
